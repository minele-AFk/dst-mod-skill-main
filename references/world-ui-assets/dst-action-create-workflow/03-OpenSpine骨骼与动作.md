# 03 OpenSpine 骨骼与动作

输入：审查过的独立 PNG、装配数据、动作规格和运行时契约。输出：真实骨架、关键帧、原生渲染及可继续编辑的项目。

## 1. 先研究工具

1. 确认安装路径、启动方式、文档、数据格式、依赖和版本。安装目录由使用者自行配置；自动化脚本统一从 `OPENSPINE_HOME` 环境变量或项目本地配置读取。
2. 先用小工程验证图片加载、骨骼继承、旋转、保存重开、IK 和图片导出，再完成 04 第 0 节的 P0 导出、编译与隔离加载验证，最后批量制作。
3. 区分编辑器、MCP、原生导出器和额外适配脚本的职责；当前 MCP 工具名称、读写保护及预览/截图边界见 [OpenSpine MCP 能力与限制](references/openspine-mcp.md)。“能读 JSON”不等于“能渲染完整动作”。
4. 记录实际构建指纹。工具源码或编译版本变化后重新验证，不假设接口永远相同。
5. 找不到其他工具时先查工具官方文档、当前团队的工具清单或项目配置；不要依赖某位维护者的个人路径记录。

## 2. 本次实际工具链

```text
部件 manifest + 动作规格
  -> 生成 Spine JSON 骨架与关键帧
  -> OpenSpine MCP 校验并受保护写入
  -> OpenSpine SkeletonLoader 加载
  -> 原生 AnimationSampler 求骨骼与约束姿势
  -> 原生 PngAnimationExporter 渲染
  -> 保存重开检查、预览编码、SCML 矩阵烘焙
```

`NativeExport.java` 是原生类的批量调用适配器，没有重写骨骼或 IK 求解器，也没有修改 OpenSpine 源码。使用的是 Region 图片附件绑定，不是网格权重蒙皮。

本次没有操作桌面编辑器窗口；MCP 与隐藏 OpenGL 导出进程使用完后退出。不能把本次记录描述成已在桌面 UI 中逐项操作验证。

### 2.1 30 FPS 采样与时间换算

新制作在 OpenSpine 母版及其伴随设置中统一使用 30 FPS。关键帧、命中、换图和约束切换按 `t = F / 30` 秒编排；F0 为首帧，F12 = 400 ms，F15 = 500 ms。原生 AnimationSampler 和 PNG 导出应显式使用 30 Hz 采样，不能只在说明文字里填写 30 FPS。

每段总帧数按动作时长确定。循环周期为 `N / 30` 秒时，导出 F0 到 F(N−1) 共 N 帧，闭合姿势 FN 可保留在工程中但不重复导出；单次动作另记最后姿势时间、实际导出张数和末姿保持时长。帧数、最后关键帧时间和媒体编码时长不是一回事。

SCML 的整数毫秒必须从绝对帧号逐帧换算：`time_ms(F) = round(F × 1000 / 30)`。F0/F1/F2/F3 对应 0/33/67/100 ms，F12 = 400 ms，F15 = 500 ms。不要累计固定 33 ms，也不要把 33 ms 网格称作精确 30 FPS。

如工具链需要中间数据适配，先在 P0 中证明姿势、时长、事件和循环边界保持，再扩展全量动作。不能通过改预览播放速度、文件标签或最终二进制 FPS 字段冒充 30 FPS。

后续如必须操作桌面 UI，遵守“启动与操作 -> UI 验证 -> 清理关闭”：自动化前记录已有窗口和本任务启动的进程，只操作本任务启动的窗口；完成或明确失败后仅关闭本任务软件。截图或自动化失败时记录错误，执行一次必要关闭后停止 UI 自动化，不继续无关尝试；不要操作或关闭使用者原有窗口，也不要通过 UI 自动化代替终端命令。

## 3. 四方向转换

| 批准素材 | 工程方向 | 最终预览 |
|---|---|---|
| 左侧面 `left` | 转为原生朝右的 `side` 分支 | right；整体镜像后得到 left |
| 正面 `front` | `down` 分支 | down |
| 背面 `back` | `up` 分支 | up |

完整姿势一致转换位置、旋转、缩放、约束目标和附件，不仅翻某几张图片。解剖左右名称不交换。四向预览固定 `left, right, down, up`，每类动作都检查方向。

每只工程内有 `side/`、`down/`、`up/` 三个分支，通过槽附件时间线选择当前可见方向。可编辑项目与预览保留 `left/side/down/up` 16 段；面向 DST 的 SCML 只保留 `side/down/up` 12 段，左方向由运行时镜像。

## 4. 骨骼结构与绑定

```text
root
  facing -> motion -> body
  body -> chest, pelvis, torso
  chest -> neck -> head -> jaw
  pelvis -> tail_base -> tail_tip
  胸/髋控制下的 upper -> lower -> paw
  motion 下的各腿 *_target
```

此图是每个方向的控制职责示意，不是逐行导出的完整层级。大狼必须有两套独立 neck/head/jaw 链，不能两头共用一个头骨。

- `facing` 负责整体朝向；`motion` 负责整体位移和接地修正；`body` 负责重心。
- `torso` 可做小幅呼吸形变；颈、头、下颌和尾段保持独立控制。
- 每个方向 4 条腿，各使用两段 IK 和一个脚掌 Transform 约束；修订动作按需控制旋转、缩放和剪切属性。
- 每只合计 12 个 IK + 12 个脚掌约束；三只总计 72 个约束。
- pivot 放在语义关节处，并补偿图片裁切偏移；不能直接把静态装配指导点当成已验证结果。

先做张嘴、抬腿、蹲低、抬头、尾部最大摆幅和死亡折叠等压力姿势。检查接缝覆盖、弯曲方向、目标可达性和显隐后，再制作完整时间线。

### 4.1 腿部与约束专项

每个个体分别填写四条腿的解剖左右、肩/髋、肘/膝、脚踝、足底锚点和支撑/抬脚时间段。正面和背面的屏幕左右会变化，不能直接复制 `bendPositive` 符号，也不能只以约束数量判定绑定成功。

| 检查 | 操作与通过条件 |
|---|---|
| 正背面攻击弯曲 | 在蓄力、命中、回收及相邻帧叠加实际关节位置，与该方向目标姿势对照。本三狼要求左右肘膝分别小幅向各自外侧弯曲，背面支撑关系与正面一致；不得同向折腿或双腿内夹。其他生物按自身设计，不机械套用外弯 |
| IK 极性与可达性 | 逐帧量测足端到目标的误差；必须切换弯曲极性时，在接近伸直的过渡姿势处理，并检查两侧相邻帧无突然翻折 |
| 脚掌控制实际生效 | 检查受控骨、来源骨、`properties`、setup mix 及动作中的 mix 时间线；采样脚掌世界角度、尺度和附件顶点，确认脚底不会随小腿旋转翻面 |
| 正背面行走贴图 | 核对四肢实际显隐、前后遮挡和缩放继承。抬脚后应显露的腿不能始终隐藏，远侧腿不能错误覆盖躯干；短缩不能靠压扁脚掌或拉出剪切伪影实现 |
| 支撑与步态 | 先标明各腿支撑段，再检查足底轨迹和身体位移。原地预览的脚可相对身体后移，须结合游戏位移判断世界接地，不能把所有足端锁死在画布上；前后足也不必处于同一画面 y 坐标 |
| 跪地死亡 | 本三狼 `death_down/up` 检查双前腿折起跪地、头胸下沉、末姿接地保持；不是把侧倒动作旋转到正背面。IK/FK 和脚掌 mix 的切换前后不能跳姿，尾巴及远侧腿层级必须同时检查 |

本次 Spine 4.3 脚掌约束用过以下 `properties` 片段，必须结合实际受控骨、来源骨和时间线使用；它不是完整约束，也不是所有版本的通用 schema：

```json
{
  "properties": {
    "rotate": {"to": {"rotate": {}}},
    "scaleX": {"to": {"scaleX": {}}},
    "scaleY": {"to": {"scaleY": {}}},
    "shearY": {"to": {"shearY": {}}}
  }
}
```

只有属性映射仍不够：核对 `mixRotate`、`mixScaleX`、`mixScaleY`、`mixShearY` 在目标动作的实际值和继承默认值，不能假设省略字段就会启用。本次局部修订保留 setup 中原有混合设置，在指定动作显式启用需要的属性，不全局改动其他动作。

在独立工作副本制作有意偏转的诊断姿势，分别采样目标属性 mix 为 0 和 1 的结果，证明控制器确实影响脚掌且方向正确；诊断关键帧不进入交付工程。生产验证保存实际矩阵、足底角度、端点误差和对照图，容差与单位先写入规格。保存重开后再检查首帧、中间帧和末帧；最终仍需原生逐帧检查和用户视觉验收。

## 5. 动作规格

本次以 30 FPS 编排，F0 是首帧，时间为 `帧号 / 30`。下表是三狼案例参数，不是通用固定时长。

| 动作 | 关键设计 | 本次帧安排 |
|---|---|---|
| `idle_loop_*` | 根部稳，身体呼吸，头尾有小幅错相 | 72 帧周期，2.4 秒 |
| `walk_loop_*` | 先定落脚和抬脚，再加重心、头尾跟随 | 大狼 32 帧；A 26 帧；B 28 帧 |
| `atk_*` | 蓄力、发力咬合、过冲、回收 | F0-F29；F15 命中 |
| `death_*` | 失衡、躯干落地、腿折叠、末姿保持 | F0-F45；F22 落地；F35-F45 保持 |

1. 先做关键姿势并检查轮廓和重心，再补中间帧和次级摆动。
2. 待机、行走、攻击使用 IK 控制足端；支撑阶段不要让脚随身体任意漂移。
3. 死亡按方向混合到 FK 折叠，侧面与正背面单独设计，避免整只悬空旋转。
4. 双头保留独立控制与适度错相，但游戏伤害事件仍按 StateGraph 契约处理。
5. 循环先检查首尾姿势与运动趋势，再增加细节；单次死亡保持末帧，不能自动回到待机。

本次真实攻击名是 `atk`，不能因通用模板写作 `attack` 就改资源名。OpenSpine 的事件标记也不会自动替代 Lua 伤害调用。

## 6. 本次纠正方法

- 死亡悬空或腿姿错误：先修主姿势与 IK/FK 混合，再用原生附件顶点和 PNG alpha 轮廓检测接地，修改工程的根部关键帧。
- 攻击 IK 目标不可达：本次曾超出可达范围约 25 px，通过降低动作中的身体高度保持支撑足目标；不以缩放最终视频掩盖。
- 原图硬接缝：先判断层级、pivot、覆盖或绘画的问题，必要时返回拆件阶段补画，不能把素材缺陷都归给工具。

## 7. 打开与复现

编辑入口是 `projects/<个体>/<个体>.json`，应与 `images/` 和 `.json.openspine.json` 伴随文件一起保留。在编辑器中使用 Animate 模式，修改骨骼后确认确实写入关键帧；自由 Pose 不是已保存动画。

当前使用说明、打开命令和依赖记录在案例归档相对路径 `output/openspine/2026-09-06-murk-wolf-C-rig-v4/OPENSPINE_GUIDE.md`。历史复现脚本与覆盖风险见 [本次案例](05-三狼案例与返工复盘.md)；不要用 V1 重建脚本覆盖后续修订。

OpenSpine 动作与预览完成只到 G5。最终还必须同版交付 SCML/PNG、官方 Mod Tools 实际编译的游戏 `anim/*.zip` 和构建校验记录，见 [最终交付规范](04-验收导出与游戏接入.md)。
