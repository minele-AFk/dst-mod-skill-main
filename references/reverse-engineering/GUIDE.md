# 混淆 Mod 的静态分析与知识记录

遵守 [开发边界](../development-contract.md)：只有明确点名授权的 Mod 才读取。普通知识维护不自动授权读取其关联 Workshop 源码或历史 Mod 笔记；这里不启动第三方 loader。

## 先查已有案例，再重新分析目标

用户明确指定要恢复的 Mod 时，先查 [Mod 笔记索引](../mod-notes/README.md) 是否有同目标记录；需要比较历史保护形态时读 [解密案例与保护形态](decryption-case-patterns.md)。后者只汇总路线与失败边界，不提供可跨 Mod 复用的密钥、映射或操作码。

已有笔记可以帮助定位文件分层、入口职责、明文范围、成功路线和未测边界。先核对 Workshop ID、版本或更新时间、文件大小/哈希和原始目录状态；相同 ID 也可能已更新，旧笔记不能替代对本次快照的检查。

## 先识别实际层次

不要只按前十行或同一魔数认定整个包使用相同编码。对已授权入口依次辨识：

1. 外层包装：字符串表、字符替换、倒序、压缩或编码。
2. Lua chunk：明文、标准 Lua 字节码或自定义 VM 数据。
3. loader：它实际如何变换输入、建立环境、加载/调用模块。
4. 每个脚本是否经过相同路径；世界生成入口是否另有包装。

LOL!、daxsg_tn 等仅是线索，不证明不可恢复、所有文件相同或必然存在反调试。优先静态跟踪明确的变换，使用目标自己的字母表/索引/常量；禁止复用另一个 Mod 猜出的映射。

## 静态恢复的证据链

保留原始文件及哈希，在独立输出目录保存每一层结果。对可逆变换给出顺序和反向重编码检查；不得执行未知 loader 来“看看会发生什么”。

恢复后区分可解析 Lua、可识别字节码与 VM 数据。语法通过只证明相应解析层；常量、导入表或反汇编不等同于完整源码和运行语义。需要 luadec/lupa 等工具时先确认实际版本、输入格式与行为；不自动安装或运行历史脚本。

本库 reverse 工具可能硬编码旧目标或路径，先读实现和 help；不得把其默认输入当成本次授权。旧工具结果不能证明新目标必用相同算法。

### 从入口到载荷的检查点

1. **冻结输入。** 对原包建立完整文件清单；至少有受保护 Lua 的 SHA-256。能覆盖全部文件时再扩大哈希基线，不能事后把部分哈希写成全包验证。
2. **分类文件。** 先标记明文、入口、包装器、VM 容器、受保护载荷和资源。不要假定所有 `.lua` 或所有 `modmain*.lua` 使用同一层变换。
3. **还原目标加载链。** 从当前入口抽取常量、分派、读取边界和载荷顺序，形成“入口 → 中间层 → 映射/VM → 业务载荷”的可核对路径。相似文件名、函数外形或旧样本成功不能代替这一步。
4. **目标专属参数就地提取。** 自定义字母表、序列化标签、操作码、常量池索引、造表偏移、255 项置换表和逆序规则都按当前快照重建。旧案例参数只能作为寻找位置的线索，不能直接套用。
5. **多路交叉核对。** 用完整映射生成结果，再以独立短明文线索检查；短词命中只能形成候选。最终以整表双射、语法和往返结果判断，不能靠几个看似合理的词宣布恢复成功。
6. **逐载荷往返。** 每个受保护文件都应能用逆变换逐字节还原原密文，并与独立提取的纯解码路径比较。只验证一个代表文件、只看词频或只看部分文件，不能证明全量恢复。
7. **按原清单交付。** `decrypted_mod/` 保留相对路径并覆盖全部明文 Lua、恢复 Lua 和原始非 Lua 资源；中间层、映射、验证 JSON 与 README 放在独立目录。文件数量或哈希不一致时，不得称为完整副本。
8. **分层报告验证。** 分别记录恢复完整性、Lua 语法检查、解码器执行、往返一致、原目录未修改和游戏运行。语法/往返通过不等于 DST 能加载，更不等于角色、UI、联机或存档行为通过。

### 运行入口、模拟环境和反调试

直接执行未知入口通常是恢复成本最高、结论最难证明的路线，也容易把反调试分支误判为“解密失败”。先判断能否静态解释入口的读取与造表逻辑；只有用户授权且隔离环境能证明边界时，才考虑运行入口。

若选择隔离解释器：

- 先核对目标 Lua 版本和语言特性，再准备兼容层。用 Lua 5.4 加垫片模拟 Lua 5.1 时，`unpack/table.unpack`、整数/浮点差异、错误文本、`debug.getinfo`、`loadstring` 和字符串库行为都要实测；垫片通过一小段样例不代表入口兼容。
- 运行环境不提供真实 shell、网络、文件写入、游戏对象、存档或业务模块；捕获 `loadfile`/`loadstring` 等边界，只保留需要检查的数据。
- 遇到环境判断、调试检查、静默退出或反调试分支时，先记录实际条件和证据，再决定是否只模拟抵达解包路径所需的返回值。模拟值属于当前样本，不写成通用 Lua 规范，也不把绕过反调试写成默认路线。
- 中途捕获到包装器或 VM 容器时，不能把它称为已截获业务源码。必须继续区分容器、解释器和载荷，直到获得可核对明文并完成往返。
- 解释器步数耗尽、正则回溯失控或分派过慢时，先给状态机设明确上限并记录终止状态；用排序区间或静态索引缩小分派范围。提高上限仍须保留超时/步数保护，避免陷入不可判定的无限循环。

目标使用 `debug.getinfo` 等运行时检查时，不要把某一单行文件的 `source`、`short_src`、`currentline` 等模拟结果当作通用规则。它们只描述该快照的检查条件；应分别记录观察、模拟和验证证据。

### 失败时如何继续

- **高熵乱码或脚本全不能解析**：先检查是否取错字母表、混合了不同层，或漏了文件级逆序；不要把一次错误结果升级为“加密不可恢复”。
- **只得到包装器**：定位真正的嵌套原型、造表循环或解码函数，不把中间层交付成源码。
- **词表只局部命中**：检查映射是否覆盖 1–255 的完整双射、索引偏移是否正确，以及候选明文是否在整文件逆序后成立。
- **字节边界异常**：保留所有原始前缀、后缀和零字节；不要为了“更像 Lua”而裁掉未知字节。
- **少量文件成功**：继续扩展到原清单中的所有受保护载荷，并逐文件往返；不能用成功样本推断全包。
- **只恢复 Lua**：把原始资源与元数据按清单复制到交付目录，再核对总文件数和哈希。
- **重跑遇到只读属性或覆盖失败**：先检查副本属性和目标路径，换新的独立候选目录重跑；不改 Workshop 原件。
- **没有 Lua 5.1 或目标运行时**：把语法检查写清实际版本；如果只做了 Lua 5.4 语法检查，不能声称通过 Lua 5.1 或 DST 加载。

### 交付前的最后核对

- 原始目录是否保持只读，原文件哈希是否未变；
- 恢复是否覆盖全部受保护载荷，并保留明文文件和资源；
- 映射是否仅对本次快照有效，是否单独保存；
- 每个载荷能否逐字节往返，是否用独立路径复核；
- 语法检查实际使用哪个 Lua 版本；
- 是否启动游戏、进入角色、验证 UI、联机、存档和重启加载。

前五项是静态恢复与交付完整性的门槛；最后一项只能由对应实机测试回答。某次任务未做游戏测试时，明确写“未验证”，不因文件能解析就补写通过。

## 何时只整理架构

无法完整静态恢复时仍可整理已直接读取的 modinfo、字符串、文件清单、资产依赖和已提供日志。明确各类结论：

| 标记 | 允许的结论 |
|---|---|
| 源码 | 从已读代码/已验证恢复结果看到的具体合同 |
| 命名 | 从目录或资源名推测的模块划分，不能确认行为 |
| 日志 | 本次已有日志实际表明的加载/触发路径 |
| 静态检查 | 解析、哈希或声明检查结果 |
| 运行 | 只有真实执行过相应环境才记录 |

“源码不可读”不证明没有可行方法；也不能以“接受不可读”为固定流程。先列明无法解析的是哪一层及缺少什么证据。

## 记录与权限

记录目标版本、原始哈希、各层操作、直接证据、推断和未测行为。普通开发优先把可泛化知识放入现有专题；目标专属细节仅在本任务授权范围写入相应笔记，仍保留将来的读取边界。

启动专服、注入、探测运行时或分析反调试需有该动作的任务授权和隔离方案；不得按旧文“专服不会触发”猜测脚本副作用。解析错误与游戏验证分别报告。
