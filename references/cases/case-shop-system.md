# 设计案例：服务端商店与商品池

保留双货币、价格来源、商品池、等级解锁、特价与刷新成本这些需求。它们是项目自己的系统，不是 DST 原版 shop 组件自动提供的接口；旧稿的完整框架与 UI 不能直接当通用可运行模板。

## 职责与命名

| 拥有者 | 事实/职责 |
|---|---|
| 玩家自定义组件，如 my_mod_wallet | 货币、个人限购、持久请求记录 |
| 商品池组件/纯数据模块 | 稳定商品 ID、产品、数量、价格与解锁条件 |
| 世界自定义组件（确需共享时） | 全分片局部共享商店级别/库存；跨分片另定权威 |
| Replica/快照 | 玩家能看到的余额、商品版本和展示价格 |
| Widget | 展示、选择、发送购买意图，不提交可信余额/最终价格 |

自定义组件使用项目前缀。原版已有同名 shop 时，不能把 AddPriceModifier/AddCurrency/RefreshShop 等项目方法写成其真实 API。

## 数据合同

商品用稳定 ID，显示名不能作服务端查找/权限依据。产品名从物品名表/项目已注册 Prefab 获得，数量为允许范围内的整数。记录币种、基础价格、解锁级别、限购与商品池版本。

折扣/加价有独立 source/key，明确乘法/加法顺序、舍入、最低价与免费商品政策。查询价格纯计算，购买时用当前权威条件重新计算；客户端旧快照不决定实际收费。

## 一次购买的可达流程

```text
请求者 + 商品 ID + 展示版本/必要意图
  → 服务端验证当前玩家、商店、距离、解锁、数量、库存与币种
  → 查询当前价格和余额，确认最终交付路径
  → 执行本次结算，失败有明确撤销/补偿
  → 记录对应限购/请求结果，更新复制展示
```

同步的小操作不必引入复杂分布式事务，但必须理解生成实体、扣款和最终交付的区别。SpawnPrefab 成功不证明玩家已收到；背包满时按设计落地、拒绝或暂存，不默默吞物品。回调会改状态时复查前置条件。

连续/重复请求是否合并由玩法决定；同一个请求不能因为重发重复收费/发货。跨断线重试使用稳定请求身份，不能只用玩家本地 Widget 的一次点击布尔。磁盘重启、独立回滚与外部支付需要更强合同，不宣称普通 Lua 表有永久恰好一次保证。

## 刷新、等级与货币

刷新确认当前成本、次数和实际生成结果后再交付新池；无可用商品时定义是否收费。限时特价的时间来源、服务器暂停与读档明确。

等级和经验是独立事实，达到阈值后计算解锁；存储双货币时分别校验不足、上限与溢出。任务/击杀奖励只由权威且可证的事件增加，不从 UI 发来的数额直接记账。

## 保存与网络

组件 OnSave 返回纯数据，OnLoad 接受旧档/缺字段；自定义版本迁移放原组件。不要直接覆盖 world.OnSave/OnLoad 丢弃其他世界数据，也不要认为 TheWorld.some_table 自动持久化。

展示数据按用途和受众裁剪；不要高频发送整个大池或给所有人暴露私人钱包。网络包定义大小/版本与解析失败行为，初次绑定读取当前快照，再监听实际变化。

## 验收

覆盖两种货币、边界数量、商品删除/版本过期、折扣结束、未解锁、背包满、重复请求、断线重连、旧档与真实远端 UI。当前没有实现或运行一个商店 Mod。
