# 设计案例：任务、任务板与奖励状态

保留玩家任务管理、任务板/池、任务物品、稀有度、UI 和奖励的职责划分。旧稿中独立项目组件、世界私有表与完整 UI 不是原版内置框架；此页提供可查证合同，具体实现进入已存在的组件/动作专题。

## 模型与稳定标识

| 对象 | 最小内容 |
|---|---|
| 定义 | 任务 ID、版本、目标类型、目标值、奖励和解锁规则 |
| 玩家任务实例 | 实例 ID、定义 ID、进度、状态、有效期与必要归属 |
| 任务板/池 | 可领取候选、刷新与共享规则 |
| 任务物品 | 所属任务/玩家的稳定身份；不依赖 UI 文本或临时 GUID |
| 展示快照 | 本地玩家可见的描述、进度、可操作状态和版本 |

稀有度、权重、难度和奖励分别定义，不能用一个显示色值兼做权限。服务端挑选候选并保存实际实例，不让客户端提交任意奖励内容。

## 状态与权威链

```text
可领取 → 进行中 → 达成条件 → 已领奖
          ↘ 放弃 / 过期 / 失败
```

“达成”和“奖励交付”分开：进度到目标不意味着已发奖，重连/载入不能再次根据进度无条件触发奖励。重复领取、共享任务和限时任务各自定义合法转移，不把一个 bool 承担所有状态。

客户端请求仅为领取/提交/领奖意图。服务端确认当前实例、所属者、条件、距离、物品和次数，再推进一次状态。主机快速路径也做同样验证。

## 三类进度

- 计数/击杀：从真实权威事件累计，核对生产端 data 与归属；一个目标的不同事件不得重复计数。
- 交付物品：确认当前实体/容器所有权、实际数量和条件，消费单件/指定数量而非删除整叠；失败保留未消费部分或明确补偿。
- 探索/交互：从权威位置与动作成功结果推进，客户端点过按钮不算完成。

保存只存最小事实，派生描述与展示色可从定义重建。定义更新时对删除目标、降低门槛、改奖励及正在进行的旧实例给迁移政策。

## 奖励交付与异常

建立本次实际奖励结果与完成记录之间的顺序和失败恢复。不能先发奖励后完全不记录，也不能先永久记已领然后丢弃失败产物。同步小操作保持清晰；涉及让出/重试/外部系统时再设计相应确认与补偿。

背包满、SpawnPrefab 失败、目标同时被消费、重复请求、服务器回滚分别定义结果。不能把一份普通 World 表描述成跨崩溃/跨分片的永久事务。

## UI、保存与所有权

任务板和任务栏仅展示可见快照；任务是否可提交由服务器最终判定。每次绑定先读初值，再监听实际复制事件。开关、换任务、Controls 重建时撤销旧监听和任务，不能以固定延迟掩盖未就绪依赖。

玩家与世界事实放各自自定义组件，用 OnSave/OnLoad；直接给 TheWorld.hoshino_data 等字段赋值不会自动保存。不得覆盖原 world 保存回调丢失已有链路。跨分片任务定义拥有者及稳定实例身份，不直接跨服务器使用 GUID 引用。

## 验收与延伸

覆盖正常达成、两个玩家争抢、重复领取/领奖、任务过期、部分交付、背包满、定义更新、保存重启与真实远端 UI。当前是设计合同，不是已运行的完整任务 Mod。
