# 本地知识查询入口

知识分为本地文档与有来源的结构化记录。实质设计、实现、审查、排错按任务主动查询；已知准确路径或记录 ID 时直接读，简单机械编辑不重复检索。先明确问题、运行端和关键词，不默认加载全部资料。

| 材料 | 用途与边界 |
|---|---|
| 50 个专题，以及组件、模式、案例、契约和工具说明 | 制作流程、API 定位与项目经验；文档存在不自动代表当前版本或实机验证 |
| [专题路由表](document-routes.json) | 从当前 50 个 `GUIDE.md` 生成结构化专题目录；模式、组件及合同/工程/案例等细节页标出主专题，供导航，不构成新事实或证据等级；实际数量以 `catalog` 为准 |
| [物品名表](../prefabs/物品名字.txt) | 按中文名定位已有代码名，再核对目标版本；无命中时不猜名称 |
| [结构化知识包](dst-engineering-kb/README.md) | 64 条事实、规则候选、反例、决策、更正和测试线索；保留原有证据等级与适用范围 |
| `references/mod-notes/`、素材及外部 Mod | 普通查询排除；仅当用户明确指定目标并授权参考时，先读[笔记索引](../mod-notes/README.md)再打开对应笔记；链接不授予额外权限，细节见[项目规则](../development-contract.md) |

术语说明：“历史证据/历史记录”指以往的源码或案例分析、来源快照/指纹和验证记录，用来追溯结论及其适用范围；不是 DST 世界或角色的旧存档，也不能证明当前版本或实机已经验证。

## 查询、读原文、应用

从 skill 根目录执行；`run.ps1` 选择项目解释器。所有查询只读原文；本地文档每次按现有文件检索，无常驻服务或文档缓存。结构化包的派生 SQLite 索引仍在项目 `.codex/cache`。

```powershell
# 入口不明确或需要案例证据：同时查询本地文档和结构化记录
& ./references/tools/engineering/run.ps1 knowledge lookup '重连 效果残留 任务清理' --mode debug --limit 4

# 制作流程、具体 API 或物品名称：可只找本地文档
& ./references/tools/engineering/run.ps1 knowledge docs '新增独立锅料理 调味 食谱' --limit 4

# 不确定旧页面归哪个专题：查询当前专题与细节页的结构化路由（默认显示前 10 条）
& ./references/tools/engineering/run.ps1 knowledge topics --query '联机' --limit 10

# 在修改检索、路由或版本记录后，运行两组知识回归
& ./references/tools/engineering/run.ps1 test_knowledge
& ./references/tools/engineering/run.ps1 test_knowledge_service

# 按命中 path/line 读取有关段落；行号是当前原文行号，哈希用于识别后续变化
& ./references/tools/engineering/run.ps1 knowledge read references/core/dst-networking-rpc/GUIDE.md --start 10 --count 50

# 重要结构化结论读取完整记录、来源和更正；原命令兼容
& ./references/tools/engineering/run.ps1 knowledge call --tool get_entry --arguments '{"id":"RULE-NET-001"}'
```

`lookup` 模式为 `architect`、`implement`、`review`、`debug`、`research`；只有明确知识维护请求才用 `kb_curator`。`--limit` 为 1–10；`read --count` 为 1–200；`topics --limit` 为 0–50。路径相对 skill，拒绝目录穿越、目录联接、受限目录和任意代码文件。`catalog` 报告实际扫描范围；`topics` 从当前 GUIDE 标题、描述、路径、支持页标题和正文生成 50 条导航记录，可用 `--query` 按同一套中英文导航别名过滤，默认返回相关度最高的 10 条，并列出细节页。`status/validate/call/serve/reindex` 保留原结构化服务语义，`status` 的 64 条只统计历史证据记录。

查询返回候选位置、命中原因、行号、摘要和内容哈希。命中结果的 `role=primary_topic` 是主流程；`role=supporting_detail` 时先读 `primary_topics` 指向的专题，再读实际需要的细节页。顶层 `primary_topic_candidates` 专门列出被结果条数截掉的主专题，应先读这些候选。无映射的普通参考仍按主题判断；路由不代替原文。需要设计依据时，再读结构化记录的 scope、来源、版本、状态和 Correction。明确“本任务采用什么、为什么适用、当前源码还要确认什么”；相关性分数不代表证据强度。测试候选 `not_run` 不得写成已执行。

查询含驼峰或下划线形式的 API 标识符时，先按完整标识符的命中数量排序，再比较词项相关度 `score`；`exact_symbol_matches` 列出这些命中，摘要也优先定位对应行。普通中文描述仍按原有词项与导航别名检索。

结构化包不可用时，`lookup` 返回 `partial` 及原因，仍提供本地文档；无匹配返回显式缺口。用准确 API 名、中英文同义词或 [专题目录](../topic-index.md) 继续定位，不将空结果说成整个领域没有知识。没有执行能力时，用 `rg` 定点搜索已授权目录或直接读已知专题；不得把失败的调用写成查询成功。

查询口语症状时，Agent 先保留对象和异常，必要时拆开相互独立的问题。例如“能量条首次为零且重进丢值”分别查 HUD 初始同步和存档恢复；命中其中一类不代表两条链均已覆盖。非空但题意不符时，使用精确概念重查，并读命中的合同，不为拿到结果而接受同词弱匹配。

结构化服务以 Python 标准库和 SQLite FTS5 工作，不需要 API Key。实际配置在 references/tools/knowledge/config.json，相对路径以配置文件位置解析，DST_KB_PATH / DST_KB_INDEX 可覆盖知识包和索引位置。stdio MCP 提供结构化记录接口，CLI 的 docs/read 才读取普通文档；工具列表中没有接口时按文件或 CLI 回退。运行中知识变更会触发过期保护；先核对实际路径和版本，再按维护命令重建派生索引/重连，不改冻结原文来消除错误。

复杂设计的关系遍历与上下文预算见 [检索策略](../engineering/dst-mod-engineering/kb-retrieval.md)，结构化接口参数见 [工具定义](../tools/knowledge/docs/mcp-tools.json)。只有当前会话真正提供 MCP 工具时才称作 MCP 查询。

## 吸收新知识与维护

仅在用户要求维护 skill/知识时更新内容。先确认现有专题是否覆盖：同主题有缺口时，把有证据的补充或纠错写回原专题；已经覆盖就复用，确实没有主题才增加普通参考文档并链接入口。不要整包复制外部 skill，或为相同主题建立第二套流程。

记录来源快照、适用条件、证据等级及与已有知识的冲突；来源事实、案例建议与本机实测分别标明。版本敏感 API 先核对目标源码。只读知识包的历史数据、来源哈希和 Manifest 不作为普通专题笔记修改；若确需更新该包，按其 Governance 在工作副本维护 canonical 数据、生成索引并校验后再替换完整版本。

融合说明和原始导入哈希见 [来源记录](../engineering/dst-mod-engineering/README.md#来源与融合范围)。后来更改的本地文件不能继续宣称与原导入哈希相同；上游许可变更按具体提交和文件核对，保留原有来源声明。新的运行结果另存任务证据，不覆盖上游历史验证或自动提升候选等级。

## 正文冲突与应用优先级

同主题先读现有专题的合同与条件，再按需追工程补充中的原始线索。历史结构化记录提供案例证据与调查方向；当前源码若已证实旧正文错误，修正对应专题并记录版本，不用更多相同旧摘要冲淡更正。

- API 先区分对象、加载环境、运行端、定义与调用者；“方法名相似”不算签名证据。
- 建议补齐触发条件、采取动作、例外和可观察结果；不把某案例的特殊实现写成所有项目的强制框架。
- 示例写明输入和未提供的依赖；完整示例保持可解析，设计常量/伪代码显式标注，不伪称可直接运行。
- 同一主题的 GUIDE、详细合同和模板一起检查，避免入口已更正、复制模板仍沿用旧错。
- 文档检索返回的是当前位置；读原文并核对上述条件，不能仅用关键词得分选择实现。

本轮正文查证见 [全库维护与接口纠错](../core/dst-source-research/references/source-research.md#2026-10-18-全库维护与接口纠错)；前轮的详细源码定位保留在同一文件。结构化历史包维持 64 条原始记录与原证据等级，维护后的本地专题通过 docs/lookup 即时检索，不需要重建它的历史索引。

## 当前维护记录与失效检测

docs、lookup 和 read 的 maintenance 字段对应 [本地维护记录](review-status.json)：

| 字段/状态 | 含义 |
|---|---|
| record_current | 当前正文哈希与本轮记录一致，不代表游戏源码仍是该版本 |
| stale | 正文在登记后变化，原维护标记不再沿用 |
| unrecorded | 没有可用的匹配记录，继续读原文与目标源码 |
| unavailable | 维护记录无效或受路径限制；文档仍可查询，但不获得维护标记 |
| structure_screened | 结构、链接、代码块/候选接口筛查 |
| content_curated | 按主题修订正文/示例，并与相关合同协调 |
| source_signatures | 组件列出的声明签名对照过本机源码；不保证全部机制/返回值实测 |

这不是新的 E0–E5 证据等级，也不提高历史案例的可信度。全局 source_snapshot 指明本轮安装包指纹，不把它称为线上最新版本。未知原生绑定仍查调用点；游戏内数值、网络、画面与声音仍按任务验收。

查询结果优先显示单篇记录的 `reviewed_on` 与 `source_snapshot_sha256`，未单独登记时才使用整库值；整库维护日期或指纹变化不覆盖已有的单篇记录。

普通查询不会自动写维护记录或改知识。用户明确要求维护后，先改原专题并保留前态，再按最终正文重算哈希、记录实际执行过的检查；代码/文档改动会使旧标记自然失效。catalog 汇报登记与失效数量，支持检查是否遗漏维护。
## 知识维护时的源文件与派生产物

区分原始记录、普通专题、派生索引和发布包。修改原始内容后重新生成其对应产物，并核对清单与哈希；不手改索引或生成包伪装源内容已更新。输出使用独立目录；复用非空输出前确认它仍是完整、未被用户修改的生成包。标记或脱敏脚本不替代实际内容审查。

正文复核只更新本次实际检查过的文档哈希与范围，保留其他文档的原记录。文件哈希只证明字节一致，不能证明所有知识已被吸收；来源覆盖还要记录内容保留、同主题归口、已有覆盖或不适用的具体理由。历史验证与当前结果分别保留，未运行候选继续标未运行。

本节吸收上游 docs/maintainers.md 与公开包构建器的源/输出、生成包归属和历史证据原则；不自动执行上游构建或替换本地冻结知识包。
